- Implementation must not begin until this written spec is explicitly approved.

============================================================
1. PRODUCT GOAL
============================================================
Build a modular server-side NPC overhaul for SCUM that makes the world feel persistent, dynamic, and alive while remaining maintainable across SCUM updates.

Core design principle:
    SCUM NPC BODY + TESLES NPC BRAIN

SCUM/UE retains low-level facilities where practical:
- Actor/Pawn representation
- CharacterMovement
- NavMesh / path following
- animations
- weapons/damage/inventory where usable
- replication

Tesles owns high-level cognition and world simulation:
- personality/traits
- stress and morale
- memory and trauma
- skills and experience
- relationships
- group leadership
- group-vs-group behavior
- zombie-world interaction
- utility decisions
- movement intents and navigation policy
- virtual/off-screen simulation
- persistence
- telemetry/map viewer

No subsystem may directly reach into unrelated subsystem internals. Stable interfaces/events are mandatory.

============================================================
2. IMPLEMENTATION PHILOSOPHY
============================================================
Priority order:
1) correctness
2) observability/debuggability
3) modularity
4) server stability
5) performance
6) behavior richness
7) visual polish

No large feature will be built on an unverified SCUM/UE assumption.
Every SCUM-facing capability must first be proven against the current server build.

A failed capability check must degrade cleanly or stop installation/runtime with a precise diagnostic. Silent partial failure is not acceptable.

4. CAPABILITY PROBE — HARD QUALITY GATE
============================================================
Before production AI is built, a probe must prove all critical SCUM integration assumptions.

Required checks:
A. Discover active NPC classes and known blueprint families.
B. Discover NPC AIController and BrainComponent ownership.
C. Stop/neutralize SCUM decision AI for a test NPC.
D. Verify SCUM does not immediately reclaim the brain, or detect/suppress reclaim.
E. Issue movement intent through the retained UE/SCUM movement stack.
F. Read movement/path state.
G. Detect target/perception events or obtain a usable perception source.
H. Trigger/observe weapon use or identify the callable weapon interface.
I. Observe damage, injury and death.
J. Spawn a Tesles-managed NPC.
K. Despawn it safely.
L. Recreate/materialize it while preserving Tesles identity/state.
M. Verify server remains stable across repeated takeover cycles.

Acceptance rule:
The full overhaul does not proceed until the minimum takeover path is green:
    SCUM brain neutralized
    + Tesles movement works
    + combat primitives remain usable
    + replication remains valid
    + SCUM does not unpredictably reclaim behavior

5. NPC IDENTITY MODEL
============================================================
An NPC is primarily a persistent TeslesNPCEntity, not an Unreal Actor.

Minimum persistent identity:
- npc_id
- creation seed
- body profile
- archetype
- skill tier
- traits
- skills
- experience
- stress/morale state
- trauma modifiers
- memories
- relationships
- group membership
- current world activity
- virtual position
- current destination
- health/injury summary

The Unreal Actor is a materialized physical representation of this entity.

============================================================
6. SCUM BODY PROFILE
============================================================
SCUM body/blueprint class is kept separate from intelligence/personality.

Known user-provided example families include blueprint names such as:
- BP_Drifter_Lvl_1 .. Lvl_5 variants
- BP_Guard_Lvl_1 .. Lvl_5 variants
- Radiation variants
- AbandonedBunker variants

The SCUM blueprint level must not directly define Tesles intelligence.

BodyProfile responsibilities:
- blueprint class
- environment variant
- physical/loadout compatibility
- SCUM-side limits discovered at runtime

============================================================
7. NPC SKILL TIERS
============================================================
Tesles Skill Tier: 1–5

Tier 1 — Untrained
- poor aim
- poor cover use
- high stress sensitivity
- weak tactical movement
- poor threat prioritization

Tier 2 — Experienced civilian
- basic combat competence
- better navigation/awareness
- archetype-specific strengths

Tier 3 — Trained
- police/security/militia level
- competent cover use
- coordinated retreat/pursuit
- better stress resistance

Tier 4 — Veteran
- ex-military/veteran behavior
- good tactical movement
- strong discipline
- strong target prioritization
- good stress resistance

Tier 5 — Elite
- rare
- high coordination and weapon handling
- high discipline and awareness
- still human: stress, wounds, surprise and numerical disadvantage remain meaningful

Skill Tier and BodyProfile may correlate but are not required to match 1:1.

============================================================
11. STRESS, MORALE AND PANIC
============================================================
Stress is dynamic 0–100 state, not a trait.

Stress sources include:
- nearby gunfire
- explosions
- near misses
- taking damage
- low health
- leader injury/death
- friend/group member death
- zombie density/proximity
- being surrounded
- enemy numerical superiority
- prolonged combat
- isolation
- darkness/environment as appropriate

Stress effects include:
- aim degradation where technically possible
- longer aim stabilization
- lower decision confidence
- higher threat sensitivity
- altered attack/retreat/cover utility
- panic behaviors at extreme values

Stress response is individually modified by:
- Fearfulness
- Courage
- Discipline
- combat experience
- trauma
- current leader influence

Suggested states:
0–20 Calm
20–40 Alert
40–60 Stressed
60–80 High Stress
80–100 Panic

Panic reactions are individual:
- flee
- freeze
- suppressive/blind fire where supported
- hide
- surrender if implemented/supported
- abandon formation
- reckless aggression

============================================================
12. MEMORY AND TRAUMA
============================================================
Memory is structured, lightweight state.

Examples:
- last enemy position
- last gunshot position
- dangerous locations
- safe locations
- known NPCs/groups
- friend deaths
- leader death
- zombie swarm encounter
- ambush survived

Trauma is not simply a permanent trait overwrite.
It is a persistent or slowly decaying modifier produced by significant events.

Initial trauma examples:
- Hypervigilance
- ZombieTrauma
- CombatAversion
- LossAnxiety
- LeaderLossTrauma
- SurvivorGuilt
- VengefulResponse

Example:
NPC witnesses close friend die nearby -> acute stress spike -> probability of persistent trauma based on relationship strength, event severity, courage, prior experience and current stress.

============================================================
15. LEADERSHIP AND SUCCESSION
============================================================
Every multi-member group has a leader. Solo member is self-leader.

Leadership suitability uses:
- Leadership trait/skill
- Courage
- Discipline
- Charisma/social influence equivalent
- experience
- loyalty/trust
- group standing
- current stress/injury

Leader affects:
- group confidence
- cohesion
- tactical coordination
- panic propagation/resistance
- high-level group order

Leader injury may trigger:
- protect leader
- retreat with leader
- temporary command degradation
- succession if incapacitated

Leader death flow:
1. LeaderKilled event
2. acute group shock
3. each member computes personal reaction
4. group enters temporary leaderless state
5. succession candidates scored
6. new leader selected
7. old leader death effects continue decaying independently
8. persistent trauma may remain for some members

New leader selection must not instantly erase morale shock.

============================================================
17. ZOMBIES AS WORLD ACTORS / PRESSURE
============================================================
Zombies must materially affect NPC life and group decisions rather than only being combat targets near players.

Zombie system has two modes:

A. FULL simulation near players
- real SCUM zombie actors where available
- NPC perception detects them
- zombie count/distance raises stress
- groups choose attack/avoid/retreat/hold position based on threat
- casualties and wounds feed memory/trauma/leadership systems

B. VIRTUAL zombie pressure away from players
- world represented by regional ZombiePressureField
- pressure derives from known/spawned zombie density proxies, region type, recent encounters and configured world rules
- virtual NPC/group travel through high-pressure areas has higher risk, slower movement and possible simulated encounters

Zombie consequences:
- stress increase proportional to density/proximity and individual fear/experience
- route avoidance for cautious groups
- aggressive/experienced groups may clear a path
- ammunition/resource consumption in virtual encounters
- injury/death risk
- leader loss possibility
- trauma acquisition
- group morale/cohesion effects
- danger memory attached to location

Examples:
1 zombie -> low threat for competent group
5 zombies -> alert/caution
20 zombies -> severe group-level threat, depending on group quality, loadout and terrain

ExMilitary/Police/Veteran groups are generally less stress-sensitive but not immune.
Untrained civilians can panic rapidly.

Zombie events must publish standardized events to EventBus; Zombies module must not directly mutate unrelated module internals.

18. UTILITY AI
============================================================
Traits never directly dictate action.

Inputs:
- traits
- skills
- stress/morale
- health
- memories
- relationships
- group order
- local threats
- zombie pressure
- leader state
- resources

Candidate actions include:
- Idle
- Roam
- Travel
- Investigate
- Observe
- TakeCover
- Attack
- Suppress
- Flank
- Pursue
- Retreat
- Flee
- Hide
- HelpFriend
- ProtectLeader
- Regroup
- Loot
- AvoidArea

Action inertia/hysteresis required.
A new action should normally need a meaningful score advantage or current-action failure condition before replacing the current action.
This prevents attack/retreat/attack oscillation.

============================================================
19. NAVIGATION ARCHITECTURE
============================================================
Utility AI outputs intent only.
Navigation is the exclusive owner of movement execution.

Example intent:
- Pursue target X
- preferred range 25m
- tactical mode flank
- urgency 0.82

Navigation components:
- NavigationCoordinator
- PathRequestManager
- RepathPolicy
- TargetPrediction
- FinalApproach
- StuckDetector
- StuckRecovery
- PathSmoothing
- NavigationDiagnostics

Anti-zigzag rules:
- no MoveTo spam every frame
- target displacement threshold
- minimum repath interval
- route age threshold
- explicit LOS/path-state triggers
- final-approach policy near target
- measurable progress/stuck detection

Navigation bugs should be repairable inside Navigation without editing Traits/Stress/Group systems.

============================================================
20. SIMULATION LOD
============================================================
Three simulation levels:

FULL
- player nearby
- real Unreal Actor
- normal movement/navigation/combat/perception

LIGHT
- intermediate distance
- Actor may exist
- reduced AI/perception/decision update rates

VIRTUAL
- no nearby player
- no expensive Actor simulation required
- entity retains position, destination, traits, stress, group, health and activity
- travel and encounters resolved at coarse intervals

Materialization:
Virtual entity -> SCUM Actor while preserving Tesles state.

Dematerialization:
SCUM Actor state captured -> Actor safely removed -> Tesles virtual entity continues.

All transitions must be observable and recoverable.

============================================================
21. VIRTUAL COMBAT
============================================================
Off-screen NPC-vs-NPC and NPC-vs-zombie fights are resolved incrementally, not instant coin flips.

Inputs may include:
- effective combat power
- member skills
- weapons/loadout abstraction
- health
- morale
- stress
- leadership
- cohesion
- terrain advantage
- surprise
- zombie pressure/count estimate

Possible outputs per simulation interval:
- wounds
- death
- ammo/resource consumption
- retreat
- pursuit
- leader death
- stress changes
- trauma
- relation changes

When players approach, virtual outcomes become the source of truth for materialized world state.

============================================================
25. PERFORMANCE SCHEDULING
============================================================
Decision rates are owned by Tesles scheduler.

Indicative design targets, configurable after profiling:
- FULL combat decision updates: several Hz, not every render frame
- FULL idle decisions: lower rate
- LIGHT: substantially reduced rate
- VIRTUAL: seconds to tens of seconds depending on activity

Movement interpolation/path following may continue at engine-required rates while high-level cognition runs slower.

============================================================
26. PERSISTENCE
============================================================
Persist at minimum:
- NPC identities
- traits
- skills/experience
- stress where meaningful
- trauma
- relationships
- group membership
- group leadership
- group relations
- memories with retention policy
- virtual positions/destinations
- injuries/health abstraction

Save format must include schema version and migration support.
A corrupt save must not silently destroy the world; create backup and recover/fail visibly.

============================================================
27. INSTALLATION / REMOVAL
============================================================
Primary managed location:
F:\SteamLibrary\steamapps\common\SCUM Server\TeslesMods\TeslesNPCOverhaul\

install.bat workflow:
1. verify expected server root
2. stop SCUM server using canonical stop behavior
3. verify process actually stopped
4. backup files that will be changed
5. bootstrap required dependencies/tools
6. install/update runtime components
7. deploy Tesles mod files
8. write install manifest with exact installed files/hashes/versions
9. run validation/capability preflight
10. if failure -> rollback + diagnostic
11. start SCUM server using canonical start behavior
12. verify SCUMServer.exe started
13. print locations of logs/viewer

Canonical user-provided start behavior includes:
SCUMServer.exe -log -MaxPlayers=64 -nobattleye

uninstall.bat:
- stop server
- read manifest
- remove only Tesles-owned files
- restore backed-up replaced files when applicable
- leave unrelated mods/files untouched
- restart server unless configured otherwise

============================================================
31. DEFINITION OF DONE FOR FIRST PRODUCTION RELEASE
============================================================
The first production release is not "done" merely because NPCs move.
It must satisfy:
- SCUM decision AI takeover is stable on supported build
- movement no longer exhibits known MoveTo spam/zigzag architecture
- individual traits/skills/stress materially influence behavior
- 1–5 member groups with Group Tier 1–5 work
- leaders and succession work
- leader injury/death affects group and individuals
- persistent trauma can result from severe events
- groups can encounter/fight other groups
- zombies affect NPC/group decisions and off-screen world simulation
- FULL/LIGHT/VIRTUAL transitions preserve state
- map viewer shows every Tesles NPC individually
- NPC details show traits/stress/stats
- map right-click can copy verified teleport command
- installer can cleanly install/update/rollback/remove
- all major systems have diagnostics and feature flags
- persistent state survives server restart

============================================================
32. ARCHITECTURAL NON-NEGOTIABLES
============================================================
1. No trait directly commands movement/combat.
2. Navigation has a single movement-command owner.
3. SCUM-specific details remain behind SCUMAdapter.
4. Unreal Actor is not the persistent NPC identity.
5. Cross-module side effects use stable interfaces/events.
6. Config/balance values are not scattered through code.
7. Every major subsystem has diagnostics.
8. Install/uninstall never blindly deletes user/server files.
9. A SCUM update may break the adapter, but should not require rewriting the core AI.
10. Correctness and observability beat feature count.

END OF SPECIFICATION
